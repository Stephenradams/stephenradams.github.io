# Waiting for Review

This week has been extremely busy, with client work, starting a new mobile project, fixes on an existing mobile and continuing with Rust study.

### The Client Work

For my main client, I've been trying to wrap up several tasks before a well-earned holiday. This has led to a cycle of completing a task and then waiting for another team member to review the changes.

I'm working on a project within a large codebase, and the client has extensive built-in systems for code review, quality, and testing—all important features. However, one issue this raises is that while waiting for a review (which can take a couple of days), you often start a new task, only to have a set of comments arrive for the previous one.

This results in frequent context switching between tasks, especially when moving from frontend to backend work. This switching can introduce bugs, as you have to move back to a feature and try to remember exactly where you were and what you were thinking at the time.

So, what is the solution? There are a few things to try:

- Make small pull requests: This makes them quick and easy to review, which should help get feedback to you faster.

- Document your work: Write a detailed PR description. This ensures the reviewer has the full picture, and it provides you with much-needed context when you return to the task after a few days.

- Seek alternative reviewers: If your usual reviewer is unavailable, ask someone else on the team. This not only speeds up the process but also helps spread knowledge across the team.

- Keep a work log: This can be a private log to record what you’ve done, where you left off, and the logic behind specific decisions you made during development.
